# 01—11 举一反三练习册

[返回起点](../00_start_here.md) · [Demo 说明](../README.md) · [学习笔记](../notes/README.md)

每题先写预测，再运行。模型相关题目不要只运行一次；应记录多次结果，区分“框架确定行为”和“模型概率行为”。

## 01 工具定义与调用请求

1. 把项目号改为 `CPP-009`。预测工具名和参数中哪个字段会变化。预期：工具仍被强制为 `get_project_power`，只有模型生成的参数随问题变化。
2. 把指定工具的 `tool_choice` 改为 `auto`。预期：模型可能调用工具，也可能直接回答，应用必须处理两种分支。
3. 删除工具描述，只保留名称。比较模型是否仍能正确构造参数。结论应讨论描述质量，而不是只记录一次成功或失败。

## 02 工具结果回传

1. 分别查询 `CPP-001` 和 `CPP-002`。预期：工具结果一个包含功率，一个包含错误；最终回答必须依据工具结果。
2. 暂时注释掉 `tool_call_id`。观察接口错误或模型无法关联结果的现象，解释调用请求与返回结果为什么必须配对。
3. 保持 `tool_choice="auto"`，换成“你知道这个项目吗？”之类的问题。预期：可能没有 Tool Calling，程序应走直接回答分支而不是访问 `[0]` 崩溃。
4. 暂时删掉系统消息中的事实约束，连续运行“查询 `CPP-002`”至少 5 次，记录模型是否猜测失败原因、推荐其他项目或补充工具未返回的信息；再恢复约束并复测。结论：模型正确调用工具，并不自动保证最终回答完全忠于工具结果，仍需提示约束、结果校验和测试集。

## 03 多工具选择

1. 分别询问功率、直径和变距时间，制作“问题—预期工具—实际工具”表。
2. 把三个工具描述改得非常相似。预期：选择稳定性下降，说明工具名称和描述属于 Agent 接口设计。
3. 增加第四个用途明显不同的工具，检查它是否会干扰原有选择。

## 04 参数提取与函数调用

1. 比较“负 6 度到正 18 度”“-6° 到 18°”和“从倒车侧六度到正车侧十八度”。记录提取参数是否一致。
2. 删掉目标角度。预期：由于 Schema 将其标为必填，模型可能追问、拒绝调用或仍产生不完整参数；应用不能假定参数完整。
3. 在工具函数中加入输入范围检查，区分“JSON 能解析”“Schema 类型正确”和“业务范围正确”。

## 05 LangChain Tool 与 Schema

1. 给 `project_id` 增加默认值，比较 `required` 数组前后变化。
2. 使用 Pydantic `Field` 添加长度或正数约束，再打印 Schema。
3. 把 docstring 改成模糊描述，观察 Schema 的结构字段不会因此消失，但模型选择工具时可能受到影响。

## 06 相同函数能否成为两个节点

基线只执行一个纯工具节点。完成下面实验，理解“节点身份、执行函数和 State 更新”是三件不同的事。

1. 将同一个 `run_pitch_time_tool` 以不同名称注册两次，并串联：

   ```python
   builder.add_node("run_1", run_pitch_time_tool)
   builder.add_node("run_2", run_pitch_time_tool)
   builder.add_edge(START, "run_1")
   builder.add_edge("run_1", "run_2")
   builder.add_edge("run_2", END)
   ```

   预期：这是允许的。两个节点读取相同角度、调用相同函数并写入同一个 `tool_result`，所以数值相同，第二次写入覆盖第一次；节点名称不同不会自动改变 State。

2. 尝试两次使用完全相同的节点名。预期：图构建器拒绝重复注册；“同一个函数可复用”不等于“节点名可以重复”。
3. 在两个工具节点之间增加 `change_target_pitch` 节点，将目标角度改为另一个值。预测第二次结果如何变化。
4. 若想同时保留两次结果，把 State 改成两个字段或带 reducer 的结果列表。解释为什么只使用一个 `tool_result` 无法保存历史。

## 07 含糊表达与工具选择边界

基线使用明确问题“查询 CPP-001 项目的桨直径”，先确认完整闭环。

1. 改回探索性问题“CPP-001 项目的 R？”。至少运行 5 次并记录模型选择。`R` 可能被理解为半径、额定参数或未知缩写；一次选中直径工具不能证明稳定正确。
2. 依次测试“桨有多大”“推进器尺寸”“额定能力”“diameter”和“rated power”，比较近义词、行业用语和中英文表达。
3. 新增 `get_project_radius` 工具，再测试 `R`。分析新增候选工具为什么可能提高语义精度，也可能增加选择冲突。
4. 给系统提示增加术语定义“本项目中 R 表示桨半径”，再比较结果。结论应区分：术语表约束、工具描述和模型自身猜测。
5. 建立至少 20 条表达的固定测试集，计算选对工具的比例。不要把单次演示当作能力评估。

## 08 Schema、Evidence 与 Artifact

1. 在副本中修改 Artifact 数值但不更新哈希。预期：Schema 仍可能通过，哈希检查失败。
2. 修改 `evidence_id` 使引用断开。比较 Schema 校验与跨对象关系校验分别发现什么。
3. 只把 `approval_status` 改成 `APPROVED`。解释为什么一个字符串不能证明真实审批。

## 09 结构化输出

1. 给风险等级增加一个不允许的值，观察 Pydantic 校验如何报告错误。
2. 把 `include_raw` 改为 `False`，比较成功时返回对象和失败诊断信息的差别。
3. 增加一个必须为正数的字段，并故意让提示产生负数。区分模型遵循指令和程序强制校验。

## 10 create_agent 与手工图

1. 分别打印两张 Mermaid 图，逐条对应 `START`、`model`、`tools` 和 `END`。
2. 增加直径工具，提出同时查询功率和直径的问题，比较两套 Agent 的消息序列。
3. 删除“必须调用工具”的系统提示，询问模型已经知道的常识。观察 Agent 可以不进入 Tool 节点直接结束。
4. 为工具设置直接返回或加入结构化响应后，判断手工图还需要补哪些路由；由此说明“核心拓扑等价”不等于复刻全部框架功能。

## 11 Checkpoint、Interrupt 与 Resume

1. 把速度改成字符串 `"abc"` 或负数。预期：流程再次暂停并返回 `invalid_input`，而不是产生 Python `TypeError`。
2. 恢复时换一个 `thread_id`。预期：它不会接着原来的暂停点运行，说明 `thread_id` 是工作流实例身份的一部分。
3. 提交 `approved=false`。预期：流程以 `BLOCKED` 结束，不执行计算节点。
4. 在 `interrupt()` 前增加一个计数或写文件操作，观察恢复时节点重新执行可能导致重复副作用。再把副作用移动到恢复之后，并思考幂等键。
5. 将 `InMemorySaver` 换成 SQLite Checkpointer，分成两个进程运行“暂停”和“恢复”，验证真正的跨重启持久化。

## 综合练习

设计一个小型流程：输入项目号和角度，缺项时暂停，完整后让模型选择查询工具，程序执行确定性计算，最后输出 Pydantic 结果。要求明确写出：

- 哪些节点由确定性代码执行；
- 哪一步允许模型选择；
- State 中保存哪些字段；
- 什么条件必须暂停；
- 哪些结果只是 `DRAFT`；
- 至少五个失败测试。
