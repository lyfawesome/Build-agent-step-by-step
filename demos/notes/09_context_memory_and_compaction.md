# 09：模型上下文、应用记忆与压缩

[学习总目录](README.md) · 来源重点：[《代码实例学习》](codex://threads/01a06600-a6e2-7302-ab03-3cda43ab87dd)后半段

## 1. 保存了历史，不等于模型看见了历史

| 层 | 保存或处理什么 | 是否受单次模型窗口限制 |
| --- | --- | --- |
| 原始记录与制品库 | 原对话、客户资料、完整工具结果、图纸/报告 | 不受同一个窗口限制，但受存储/权限/保留策略限制 |
| 应用 State / Checkpoint | 当前流程、结构化事实、消息/产物引用 | 可持久化，不代表全部会送模型 |
| 本次模型上下文 | 此次请求实际选择的指令、消息、工具定义、资料 | 受当前端点和模型限制 |

本项目 Chat Completions 教学通过 `messages` 显式传历史。模型看起来记得上一轮，是因为请求提供了相关上下文，不是训练权重因本次聊天发生了持久改变。

服务端会话、缓存或其他状态化接口可以减少客户端重传，但依然要为推理提供上下文。因此不宜概括成“所有 API 在实现上完全无状态”。

## 2. LangChain 是否自动处理超长上下文

不能假设只导入 LangChain、只调用 `invoke` 就会自动安全摘要。需要选择并配置裁剪、摘要中间件、检索、结果限长或自定义上下文构造策略。模型/服务定义输入与输出限制，框架不能突破它。[短期记忆说明](https://docs.langchain.com/oss/python/langchain/short-term-memory)

做预算时需计入系统规则、消息、工具 Schema、检索内容、工具输出以及生成预留，思考 token 的计入方式也按端点确认。不能仅用字符串长度精确当 token 数，也不能只数用户问题。

Checkpoint 解决恢复问题；前缀缓存可能减少重复计算；更大窗口提供更多空间。三者都不能代替上下文选择或保证长历史中的事实不被忽略。

## 3. 五种管理方式

| 方法 | 怎么做 | 风险/边界 |
| --- | --- | --- |
| 临时裁剪 | 存储保留完整记录，本次只选部分消息 | 被排除的事实要能重新取回 |
| 状态裁剪 | 删除活动 State 中旧消息 | 若需审计，应事先独立留存，不能假定永远可恢复 |
| 摘要 | 用较短摘要替换旧讨论，保留近期消息 | 可能遗漏数值、条件、来源和用户纠正 |
| RAG | 每次检索当前任务相关片段 | 需权限过滤、版本/适用性、引用验证 |
| 工具结果外存与节点投影 | 大结果存文件/库，返回 ID、关键指标；每个节点只看必要字段 | 再查询接口也要授权与版本绑定 |

裁剪必须保持协议有效：不要只剩工具结果而丢掉对应调用，或丢掉未完成调用的结果。摘要不应将未执行、未批准的动作写成完成。

## 4. 压缩后是否变成全新对话

是新的一次模型推理，但不一定是新应用任务，更不是“完全没上下文”。

```text
之前：固定规则 + 较早历史 + 近期历史 + 当前问题
之后：固定规则 + 历史摘要 + 当前结构化事实 + 近期历史 + 当前问题
```

同一个 `thread_id` 或工程 `run_id` 可以继续，数据库记录与文件不因摘要自动消失。压缩改变的是当前可见材料，不能拿摘要覆盖原始批准基线。

## 5. “正在压缩上下文”通常在干什么

一般工程模式是先估计用量，筛选较旧或可重取的资料，裁剪大工具输出；必要时生成任务摘要；保留近期消息和未完成调用关联；用更短上下文继续。它不是压缩模型权重，也不是 token 的无损压缩算法。

一个任务摘要应保留：目标、用户约束、已完成/未完成事项、关键决定及原因、文件/符号/运行 ID、错误与测试结论、阻塞和下一步。文件全文或重复日志可外存后按需重取。

**不能把所有产品都说成“必然生成一段可读摘要”。** OpenAI Responses 的压缩机制可产生不透明的加密状态项，应整体按协议传回，而不是解析成普通说明文字。[OpenAI Compaction](https://developers.openai.com/api/docs/guides/compaction)

指定对话还讨论了 Codex、Claude Code 和 DeepSeek Harness。保留的稳定结论是：产品/harness 管理当前上下文，外部文件和状态支持连续工作。内部提示词、触发百分比、保留比例、事件格式依产品和版本而变；历史答复提过的具体比例不作为本项目配置常量，也不能据公共 API 文档断言每个产品内部实现完全一样。

## 6. 面向调距桨项目的上下文策略

- 精确输入保存在结构化工程记录中，包含单位、来源和确认状态。
- 证据、规则、产物保存版本与引用，模型只接收当前可用子集。
- 摘要主要保存任务进展和讨论过程，不成为工程事实的唯一存储。
- 关键节点重新读取当前修订事实及批准记录，不能依靠“模型记得已审核”。
- 大型计算日志只给模型必要摘要与回查 ID，不把海量原始输出每轮重发。
- 每个节点建立自己的输入投影：解析看原文，计算看已确认数值，报告看冻结结论和依据。
- Token 预算、摘要触发点、近期消息数量需按实际请求测试，不直接套用模型标称窗口。

## 7. RAG 与长期记忆的定位

RAG 常见路径是文档加载 → 切分 → 向量/关键词索引 → 权限和型号/版本过滤 → 检索与重排 → 选段供模型使用 → 引用核查。Embedding 是向量表示，不是完成了生成模型训练。

专业资料中型号、报警码、部件编码常需关键词或混合检索；语义相近不等于适用于当前船型和规范版本。未接受控资料时，应列为待接入能力，不能编造知识清单。

长期记忆是存储和取回机制，不代表所有历史都持续在模型上下文中。框架组件提供能力，不等于当前 01—08 demo 自动拥有完整知识库或摘要器。
